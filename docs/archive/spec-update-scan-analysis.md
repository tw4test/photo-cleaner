# 更新需求：掃描與分析拆分為獨立功能

> 適用版本：相片瘦身 P1 之後的修改。本文只涵蓋「掃描」與「分析」兩部分。
> 「評估（規則引擎）」的拆分尚待決定，見第 9 節。

---

## 1. 目標

把「掃描」「分析」做成互不依賴、可單獨執行的功能：

- **掃描**只負責讓資料庫知道有哪些檔案，不讀圖片內容
- **分析**只處理尚未完成的項目，每一段都可單獨執行、單獨重試，並可指定使用 GPU 或 CPU
- 資料庫要能明確回答「這張相片的哪一段分析完成了、用什麼模型、有沒有失敗」

## 2. 現況與問題

| 編號 | 問題 |
|---|---|
| P-1 | 掃描除了新增，還會處理「檔案被修改」與「檔案消失」，無法選擇只加入新檔案 |
| P-2 | 分析的三段（雜湊、相片特徵與 CLIP、影片資訊）綁在同一個工作與 API，不能單獨執行 |
| P-3 | 相片特徵與 CLIP 在同一次寫入，換 CLIP 模型時無法只重算 CLIP，必須連模糊、亮度、縮圖一起重做 |
| P-4 | 資料庫不記錄 CLIP 向量由哪個模型產生。換模型後舊向量仍被視為「已分析」，不同維度的向量會混用 |
| P-5 | `files.sha256` 為 NULL 時，分不出是「還沒算」還是「不需要算（大小唯一）」 |
| P-6 | 解碼失敗的相片留下失敗記錄後不會再被處理，也沒有重試入口 |
| P-7 | 縮圖檔被刪除後，資料庫仍認為分析完成，審核頁只會顯示「無縮圖」 |
| P-8 | GPU／CPU 只能在設定頁全域切換，不能在執行分析時選擇 |

---

## 3. 掃描需求

| 編號 | 需求 |
|---|---|
| S-1 | 掃描提供兩種模式：**完整掃描**（預設）與**只加入新檔案** |
| S-2 | 完整掃描：新增資產；偵測大小或修改時間改變的檔案，清除其分析結果並重置審核狀態；偵測消失的檔案並標為 `missing`（維持現有行為） |
| S-3 | 只加入新檔案：僅新增資產。**不**清除已修改檔案的分析結果，**不**標記任何資產為 `missing` |
| S-4 | 兩種模式都**不讀取圖片內容**，不做任何分析 |
| S-5 | 掃描結束時回報摘要：新增、修改、消失、不變各幾個資產 |
| S-6 | 離線的路徑仍標為「不可用」並略過，不影響其資產狀態（維持現有行為） |
| S-7 | 仍支援 RAW+JPG、Live Photo、側車檔的配對（維持現有行為） |

## 4. 分析需求

### 4.1 拆成四個獨立階段

| 階段代號 | 名稱 | 內容 | 對象 |
|---|---|---|---|
| `hash` | 檔案雜湊 | SHA-256，僅處理與其他檔案大小相同者 | 所有主檔 |
| `basic` | 相片基本特徵 | 縮圖、模糊分數、亮度、pHash、EXIF、尺寸 | 相片與 RAW |
| `clip` | CLIP | 向量、零樣本標籤 | 相片與 RAW |
| `video` | 影片資訊 | ffprobe 時長與尺寸、第一幀縮圖（不解碼分析） | 影片 |

| 編號 | 需求 |
|---|---|
| A-1 | 每個階段可單獨執行，也可選擇多個階段依序執行；提供「全部分析」 |
| A-2 | 每個階段只處理**尚未完成**的資產，可暫停、取消、續跑 |
| A-3 | 「全部分析」時，`basic` 與 `clip` 若同一張相片都待處理，**合併為一次讀圖**，避免重複解碼（尤其是 RAW、HEIC） |
| A-4 | 單張失敗只記錄，不中斷該階段 |

### 4.2 各階段的完成標記

| 階段 | 已完成 | 待處理 | 失敗 | 過期 |
|---|---|---|---|---|
| `hash` | `hash_state = 'done'` | `'pending'` | `'error'` | — |
| `basic` | `features.decode_status = 'ok'` 且縮圖檔存在 | 無 `features` 記錄，或縮圖檔不存在 | `decode_status = 'error'` | — |
| `clip` | `clip_features` 有記錄且模型與目前設定相同 | 無記錄 | 讀圖失敗 | 模型與目前設定不同 |
| `video` | `video_info` 有記錄 | 無記錄 | — | — |

### 4.3 雜湊狀態明確化（對應 P-5）

| 編號 | 需求 |
|---|---|
| A-5 | 新增 `files.hash_state`，值為 `pending`、`done`、`not_needed`、`error` |
| A-6 | `not_needed`：該檔案大小在所有作用中資產內唯一，不需要算雜湊 |
| A-7 | 每次執行 `hash` 階段時，重新檢查 `not_needed` 的檔案：若後來有大小相同的檔案加入，改為 `pending` 並計算 |

### 4.4 運算裝置選擇（對應 P-8）

| 編號 | 需求 |
|---|---|
| A-8 | 執行分析時可選擇裝置：**自動**、**只用 GPU**、**只用 CPU**。預設值取自設定頁，但只對本次執行有效，不改動全域設定 |
| A-9 | 選擇「只用 GPU」但 CUDA 不可用時，**直接報錯並說明原因**，不靜默退回 CPU |
| A-10 | 選擇「自動」時，無 GPU 才退回 CPU，並在進度列顯示實際使用的裝置 |
| A-11 | 裝置選擇只影響 `clip` 階段（其餘階段不使用 GPU） |

### 4.5 CLIP 模型追蹤（對應 P-3、P-4）

| 編號 | 需求 |
|---|---|
| A-12 | CLIP 結果獨立存放，並記錄產生它的模型名稱、預訓練權重、向量維度 |
| A-13 | 設定中的模型與資料庫記錄不同時，這些相片的 `clip` 階段視為**過期** |
| A-14 | 存在過期資料時，分析頁顯示警告，例如「有 N 張是用舊模型分析的」，並提供「只重算 CLIP」按鈕 |
| A-15 | 只重算 CLIP 時，**不重跑** `basic`（不重算模糊、亮度、pHash、縮圖） |
| A-16 | 重算 CLIP 前必須確認，並說明近似與連拍的門檻可能需要重新校準 |
| A-17 | 評估規則時，**只使用與目前設定相同模型的向量**；被排除的相片數量要明確提示，不可混用不同模型的向量 |

### 4.6 失敗處理與補救（對應 P-6、P-7）

| 編號 | 需求 |
|---|---|
| A-18 | 提供失敗清單：階段、路徑、錯誤訊息，可檢視 |
| A-19 | 提供「重試失敗項目」，可針對單一階段或全部階段 |
| A-20 | 提供「補算缺少的縮圖」：只針對縮圖檔不存在的相片，只重跑縮圖，不動其他分析結果 |

### 4.7 分析狀態總覽

| 編號 | 需求 |
|---|---|
| A-21 | 分析頁顯示每個階段的統計：待處理、已完成、失敗、過期（若適用） |
| A-22 | 顯示目前設定的 CLIP 模型與運算裝置 |

## 5. 資料模型變更

### 5.1 `files`

| 變更 | 說明 |
|---|---|
| 新增 `hash_state TEXT` | `pending`、`done`、`not_needed`、`error` |

### 5.2 `features`（只保留基本特徵）

| 變更 | 說明 |
|---|---|
| 移除 `clip`、`zs` 欄位 | 搬到 `clip_features` |
| 保留 | `decode_status`、`error`、`phash`、`blur`、`brightness`、`dark_ratio`、`bright_ratio`、`width`、`height`、`taken_at`、`taken_src`、`exif`、`analyzed_at` |

### 5.3 新增 `clip_features`

| 欄位 | 說明 |
|---|---|
| `asset_id` | 主鍵，對應 `assets.id`，刪除資產時連帶刪除 |
| `model` | 例如 `ViT-B-16` |
| `pretrained` | 例如 `laion2b_s34b_b88k` |
| `dim` | 向量維度 |
| `embedding` | 向量（BLOB） |
| `zs` | 零樣本機率（JSON） |
| `analyzed_at` | 時間戳 |

### 5.4 遷移

| 編號 | 需求 |
|---|---|
| M-1 | 用 `PRAGMA user_version` 管理資料庫版本 |
| M-2 | 升級時，把既有 `features.clip`、`features.zs` 搬進 `clip_features`，`model` 與 `pretrained` 填入**升級當下設定中的值** |
| M-3 | 既有 `files.sha256` 有值者，`hash_state` 設為 `done`；其餘設為 `pending` |
| M-4 | 遷移必須可重複執行而不損壞資料，執行前自動備份資料庫檔案 |

## 6. API 變更

| 端點 | 變更 |
|---|---|
| `POST /api/jobs/scan` | 新增參數 `mode`：`full`（預設）或 `new_only` |
| `POST /api/jobs/analyze` | 新增參數 `stages`（`hash`、`basic`、`clip`、`video` 的子集，預設全部）、`device`（`auto`、`cuda`、`cpu`）、`retry_failed`（布林） |
| `POST /api/jobs/rebuild_thumbs` | 新增：只補算缺少的縮圖 |
| `GET /api/analysis/status` | 新增：各階段統計，以及目前設定的 CLIP 模型與裝置 |
| `GET /api/analysis/failures` | 新增：失敗清單，可依 `stage` 篩選 |

## 7. 介面變更

「路徑與掃描」頁分成三塊，各自獨立操作：

| 區塊 | 內容 |
|---|---|
| **掃描** | 模式選擇（完整掃描／只加入新檔案）、按鈕、上次掃描摘要 |
| **分析** | 四個階段各一列，顯示統計與「執行」按鈕；裝置選擇；「全部分析」「重試失敗」「補算縮圖」；CLIP 過期警告 |
| **評估** | 維持現有的「重新評估規則」按鈕（待第 9 節決定後調整） |

「一鍵執行」保留，依序執行完整掃描、全部分析、評估。

## 8. 驗收條件

| 編號 | 條件 |
|---|---|
| T-1 | 「只加入新檔案」模式下，修改過的檔案其分析結果保留，消失的檔案不會被標為 `missing` |
| T-2 | 單獨執行 `hash` 時，不讀取任何圖片內容 |
| T-3 | 單獨執行 `clip` 時，`features` 表內的模糊、亮度、pHash 不被改動 |
| T-4 | 「全部分析」處理同一張新相片時，圖片只被解碼一次 |
| T-5 | 換 CLIP 模型後，舊向量的相片被標為過期；評估時不使用這些向量並顯示被排除的數量 |
| T-6 | 選「只用 GPU」但無 CUDA 時，工作直接失敗並顯示原因；選「自動」時退回 CPU 並顯示 |
| T-7 | 刪除 `data/thumbs/` 內的部分縮圖後，「補算縮圖」只補缺少的，其餘分析結果不變 |
| T-8 | 有解碼失敗的相片時，「重試失敗項目」會重新嘗試；仍失敗則保持失敗狀態 |
| T-9 | 一個 `hash_state = 'not_needed'` 的檔案，在新增了大小相同的檔案後，下次執行 `hash` 會被改為 `pending` 並算出雜湊 |
| T-10 | 舊版資料庫升級後，既有分析結果完整保留，`clip_features` 的模型欄位為升級當下的設定值 |
| T-11 | 所有階段仍可暫停、取消、續跑；中斷後續跑不會重複處理已完成的項目 |
